# Combat drawer, zoom and token synchronization

The map opens at 100%. Fit map explicitly enables responsive fitting; hidden or unmeasured viewports do not change the zoom. Clicking the percentage returns to 100% and stops automatic fitting.

Both Turn order and Combat panel open the same native modal drawer above the map, including the session embedding and native fullscreen. It traps keyboard focus, restores the opener on dismissal and yields Escape to reroll/end confirmations. Pending operations cannot dismiss the drawer. Show on map closes the drawer and focuses the map.

An empty panel offers Prepare combat. During an existing combat, Add new tokens to combat appends missing map tokens with initiative 0, preserving existing rolls, turn order and the current participant. Roll the newcomers individually when ready. Repeated additions use `ON CONFLICT (scene_id, token_id) DO NOTHING`; the matching `initiative_token_unique` index was verified read-only on Production on 2026-11-06. No migration was applied. As with the existing combat actions, concurrent end/prepare/reorder operations across different clients are not a single transaction.

Token movement no longer uses a 500ms ignore window. Each mounted token serializes its saves and coalesces waiting destinations to the latest local intent. Earlier responses cannot replace a newer queued destination. Successful actions return canonical coordinates and the database `updated_at`; stale props and broadcasts cannot rewind an acknowledged move. Postgres microseconds are retained when comparing revisions. The actual Realtime hook also rejects older row revisions in broadcasts, server props and reconnect snapshots. Wall collision and pointer cancellation use the current local movement state; pointer listeners and timers are cleaned up on unmount. Already requested moves finish without notifying an unmounted component.

An explicit rejection restores the latest known authoritative location only when no newer move is waiting. A lost response retains the local location and reports an uncertain result rather than automatically retrying. This is per-client reconciliation, not distributed locking or a guarantee of ordering between two people moving the same token. The database timestamp is the existing update timestamp, not a newly introduced global sequence.

Regression coverage runs the real Token component and `useRealtimeTokens` against a disposable in-memory Supabase boundary, with deferred writes, old broadcasts, stale server props, and reconnect snapshot races. Other tests cover hidden session panes, native drawer focus and nested confirmations, preparation, and adding three reinforcements without changing the existing queue. No player tokens, live combat, HP, storage or database schema are mutated by these tests.
